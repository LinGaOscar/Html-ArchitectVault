長時間工作：同步等待 vs 輪詢 vs 推播

生活情境按下「匯出年度報表」，要跑一兩分鐘。畫面一直轉圈，最後卻跳出錯誤；重按一次，後台又多做一份。

打個比方同步等待像站在洗衣店櫃台等衣服洗好；輪詢像拿了取件單，每隔十分鐘打電話問「好了沒」；推播像留下電話，洗好由店家主動通知。

這頁比較後端工作要做很久時，前端和後端溝通的三種方式。

建議先看：前端呼叫 API

匯出報表、轉檔、批次匯入這類工作要跑幾十秒到幾分鐘。讓一個請求一路等到做完最簡單，但請求會撞上等待時間的上限（逾時），連線也一直被佔著。常見的做法是先回覆「收到了」，把工作交給後台，再用輪詢或推播告訴前端什麼時候做好。

每個面板有三條泳道：瀏覽器、伺服器入口、後台工作。黃色是被佔住的連線，紫色是後台真正在做的報表。留意第 60 秒同步等待發生了什麼，以及三種做法各在第幾秒讓使用者拿到報表。

重點整理

同步等待
前端一個請求等到底。工作超過等待上限，使用者就看到錯誤，後台卻還在做；使用者重按，又多做一份。等待期間連線一直被佔著，同時的人一多，伺服器就撐不住。
為什麼這樣設計這是最原始、最簡單的做法，前後端都不需要額外的機制。工作幾秒內一定做完時，這份簡單是值得的。
先回「收到了」＋輪詢
伺服器立刻回覆「收到了」和工作編號，工作交給後台；前端每隔一段時間問一次進度。每次詢問都很短，不怕逾時；代價是大多數詢問都白問，而且結果最多晚一個間隔才知道。
為什麼這樣設計把「接下工作」和「做完工作」拆開，請求長短就不再受工作時間影響。輪詢只用最普通的請求，任何伺服器和網路設備都支援，是最穩妥的做法。
先回「收到了」＋推播
同樣先回覆「收到了」，前端保持一條連線，伺服器在做完的那一刻主動通知。沒有白問，也沒有延遲；代價是伺服器要能同時維持大量閒置的連線，斷線時還要重新連上。
為什麼這樣設計使用者正盯著畫面等（進度條、聊天、即時通知）時，晚幾秒都感覺得到，一直白問也浪費資源。讓「事情發生的一方」主動通知，即時又省資源。
跟其他主題的關係
後台工作通常靠訊息佇列分派（見 Kafka vs RabbitMQ）；「先回收到、稍後才完成」也是最終一致的一種（見 CQRS）。
