CQRS：CRUD vs CQRS vs Event Sourcing

生活情境下單之後馬上去看「我的訂單」，新訂單卻還沒出現；或是財務想查某筆訂單改過幾次價，系統裡卻只剩最新的金額。

打個比方傳統做法像只有一本帳冊，記帳和查帳都用它；CQRS 像記帳一本、另外整理一本給人查；Event Sourcing 像存摺明細，不只記餘額，每一筆進出都留著。

這頁比較「寫資料」和「查資料」用同一套還是分開，以及要不要把發生過的每件事都留下來。

建議先看：Kafka vs RabbitMQ

一般系統用同一組資料表處理寫入和查詢。可是寫入要守規則、避免重複；查詢要照畫面整理好、讀得快。CQRS 把兩者拆成兩套資料；Event Sourcing 更進一步，寫入時只記錄「發生了什麼事」，所有查詢資料都由這些事件整理出來。

三個面板處理同一串訂單。留意 CQRS 剛下完單時查詢資料標成「舊資料」的那一拍、查列表時 CRUD 被標成「綁住」的資料表，以及新增報表時只有 Event Sourcing 找得回改價和取消的紀錄。

重點整理

傳統 CRUD（一本帳冊）
讀和寫用同一組資料表，寫進去的下一刻就讀得到，最簡單。查詢畫面越多、越複雜，就越常要把好幾張表對起來，讀和寫也搶同一組資源。
為什麼這樣設計大部分系統的讀寫需求差不多，一組資料表最好理解，現成工具也都支援，而且沒有同步延遲。不需要更複雜的時候，它就是最好的選擇。
CQRS（記帳本與查詢本分開）
寫入那一邊專心守規則；查詢那一邊存照畫面整理好的資料，讀得快，也能單獨加開。兩邊靠同步程式串起來，所以查詢那邊會晚一步（最終一致），畫面要能接受「剛送出還沒看到」。
為什麼這樣設計寫入要守規則、避免資料不一致；查詢要快，量往往還大好幾倍。用同一套資料，兩邊都得妥協；拆開之後，就能各用最適合的方式，也能各自擴充。
Event Sourcing（存摺明細）
不存「現在的樣子」，只依序記下發生過的事（下單、改價、取消）。目前狀態和各種報表都由這些事件整理出來，所以有完整的歷史紀錄，也能隨時重新整理出新的報表。代價是事件格式要長期維護，事件很多時重新整理要花時間。
為什麼這樣設計在金流、訂單這類領域，「怎麼走到現在」和「現在是什麼」一樣重要，稽核、對帳、處理糾紛都需要。只存目前狀態會丟掉歷史；把事件當成真相，任何時間點、任何角度的資料都能重建。
和 Kafka 的關係
Event Sourcing 的「只往後加、可以重讀」和 Kafka 的帳本是同一個想法。實務上常用 Kafka 把事件送給各個同步程式。
