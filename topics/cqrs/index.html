CQRS：CRUD vs CQRS vs Event Sourcing

一般系統用同一個模型、同一組資料表處理讀和寫。可是寫入要的是正規化、守住業務規則；查詢要的是照畫面組好、讀得快。CQRS（Command Query Responsibility Segregation）把兩者拆成不同的模型與資料庫；Event Sourcing 更進一步，寫入端只記錄「發生過什麼事」，所有狀態都由事件推導出來。

三個面板處理同一串訂單。留意 CQRS 剛下完單時讀取端標成「舊資料」的那一拍、查列表時 CRUD 被標成「綁住」的資料表，以及新增報表時只有 Event Sourcing 能把改價、取消的歷史找回來。

重點整理

傳統 CRUD
讀寫共用模型與資料表，寫進去下一刻就讀得到，最簡單。查詢畫面越多越複雜，就越常要 JOIN 多張表，讀寫也搶同一組資源。
為什麼這樣設計大部分系統的讀寫需求差不多，一個模型、一組資料表最容易理解，框架與工具也都支援，而且沒有同步延遲。複雜度不必要時，它就是最好的選擇。
CQRS
Command 端專心守業務規則、寫正規化資料；Query 端存照畫面組好的 view，讀起來快、能單獨擴充。兩邊靠 Projector 非同步同步，所以讀取端會晚一步（最終一致），畫面要能接受「剛送出還沒看到」。
為什麼這樣設計寫入要守業務規則、要正規化避免不一致；查詢要照畫面組好、要快，量往往還大好幾倍。用同一個模型兩邊都得妥協，拆開之後就能各用最適合的結構與資料庫，也能各自擴充。
Event Sourcing
不存目前狀態，只依序追加事件（OrderPlaced、PriceChanged、OrderCancelled）。目前狀態、報表都是由事件投影出來的，所以有完整稽核軌跡，也能隨時重播事件建出新的 view。代價是事件格式的版本管理、事件很多時的重播時間（通常搭配快照）。
為什麼這樣設計在金融、訂單這類領域，「怎麼走到現在的狀態」和狀態本身一樣重要，稽核、對帳、處理爭議都需要。只存目前狀態會丟掉歷史；把事件當成真相，任何時間點、任何角度的資料都能重建。
和 Kafka 的關係
Event Store 的「只追加、可重播」和 Kafka 的 log 是同一個想法。實務上常用 Kafka 把事件送給各個 Projector，但 Event Store 本身需要依訂單讀出事件、檢查版本衝突，通常另用專門的資料庫。
