畫面互動模式：MVC vs MVP vs MVVM

生活情境購物車改了數量，總價、購物車圖示、結帳按鈕好幾個地方都要跟著變；漏改一處，畫面就對不起來。

打個比方MVC 像公布欄，資料一改，大家自己來看；MVP 像秘書，一個一個打電話通知；MVVM 像共用的雲端試算表，一改所有人的畫面自動同步。

這頁比較畫面和資料之間的三種串接方式：資料改了以後，由誰負責把它送回畫面。

畫面程式最容易變成一團：處理點擊、計算、更新畫面全寫在一起，改一個地方牽動一大片，也很難測試。MVC、MVP、MVVM 都把畫面和資料分開，再用中間一層串起來，差別在「資料改了之後，誰把它送回畫面」。

三個面板的畫面元件和資料完全一樣，只有中間那一層不同。留意數量改了之後幾拍才更新完畫面、誰在主動去改畫面，以及多一個畫面元件、寫測試時哪些方塊被標成「要改」「綁住」「假的」。

重點整理

MVC（公布欄）
Controller 接收使用者的操作並修改資料，畫面自己盯著資料，資料一變就自己重畫。分工直覺，但畫面直接綁著資料，處理畫面的程式容易分散在好幾處，也不好脫離畫面來測試。
為什麼這樣設計最早是為了讓同一份資料能用多種方式呈現（表格、圖表），把資料和顯示分開。網站伺服器「收到一個請求、交給一個 Controller、回一個頁面」也剛好符合這個分工。
MVP（秘書）
畫面變成被動的，只把操作交給 Presenter；所有畫面邏輯集中在 Presenter，由它決定什麼時候更新哪個畫面。好測試；代價是每個畫面元件都要寫對應的更新程式，畫面越多，Presenter 越肥。
為什麼這樣設計在沒有自動同步功能的畫面框架裡，畫面很難測試。把畫面邏輯全搬進 Presenter，畫面只剩一組規格，就能用假的畫面來測試。
MVVM（共用試算表）
ViewModel 只提供畫面需要的值（數量、總價），畫面宣告「我要顯示總價」，由框架自動同步。ViewModel 不認識任何畫面，最好測，加畫面也不用改它；代價是要依賴這套自動同步的框架，出問題時比較難追。
為什麼這樣設計有了自動同步的框架之後，「把值填到畫面上」這種程式可以交給框架做。ViewModel 只描述畫面需要的狀態，改畫面和寫邏輯可以分開進行。
怎麼選
通常由使用的框架決定：網站伺服器端的框架多半是 MVC；Vue、Angular、SwiftUI 這類有自動同步的前端框架走 MVVM。沒有自動同步、又需要好測試時，才自己寫 MVP。
