程式內部分層：三層式 vs 六角架構 vs Clean Architecture

一個應用程式的程式碼要怎麼分層，決定了改需求時會牽動多少地方。三層式依照「展示、業務、資料」由上往下堆；六角架構和 Clean Architecture 則把業務邏輯放在中心，讓資料庫、Web 框架這些外部的東西反過來依賴它。三者執行起來的呼叫路徑差不多，差別在原始碼的依賴方向。

箭頭代表「誰 import 誰」，實線是依賴具體類別，虛線是依賴介面。留意綠色的業務邏輯有沒有往外指的箭頭，以及換資料庫、寫單元測試時，哪些方塊被標成「要改」或「綁住」。

重點整理

三層式（Layered）
最直覺也最常見。每層只呼叫下一層，但業務邏輯直接依賴資料存取類別，資料庫換了或想脫離資料庫測試時，業務邏輯就會被牽動。若在業務層和資料層之間加上介面（依賴反轉），它就往六角架構靠攏了。
為什麼這樣設計把畫面、規則、資料分開，讓結構好理解，不同專長的人也能各負責一層。以 CRUD 為主的系統，業務規則本來就很薄，多加一層介面只是負擔。
六角架構（Ports & Adapters）
核心定義自己需要的 Port 介面，外面的 Adapter 去實作或呼叫它。資料庫、HTTP、訊息佇列都只是可替換的 Adapter，由 main 在啟動時組裝起來。
為什麼這樣設計Alistair Cockburn 希望應用程式「不靠 UI、不靠資料庫」也能被執行和測試。把外部世界都當成可插拔的 Adapter，業務核心就能獨立演進，換框架、換資料庫都不必動到它。
Clean Architecture
和六角架構同一個家族，再把核心細分成 Entity（企業規則）和 Use Case（應用規則），依賴一律由外圈指向內圈。分得越細越能隔離變化，也越容易對小專案過度設計。
為什麼這樣設計大型、長壽的系統裡，框架、資料庫、UI 都可能換好幾輪，只有業務規則一直留著。用同心圓強制依賴只能往內，最穩定的東西放最裡面，越外圈越容易替換。
依賴反轉
三者的關鍵差異都來自一件事：讓高層的業務邏輯依賴抽象介面，而不是依賴低層的實作。執行時的呼叫方向不變，原始碼的依賴方向反過來。
