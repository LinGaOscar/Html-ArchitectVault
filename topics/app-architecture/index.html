程式內部分層：三層式 vs 六角架構 vs Clean Architecture

生活情境公司決定換一套資料庫，結果整個系統的程式都要改，連核心的計價規則都得重新測一遍。

打個比方電器直接焊死在牆上的電線（三層式），換一種電源就得拆牆；改用插座和插頭（六角架構），換電源只要換插頭，電器本身不用動。

這頁比較程式碼的三種分層方式，在「換資料庫、寫自動測試」時各要動到多少程式。

一個系統的程式碼要怎麼分層，決定了改需求時會牽動多少地方。三層式依「畫面、規則、資料」由上往下疊；六角架構和 Clean Architecture 則把業務規則放在中心，讓資料庫、網頁框架這些外部的東西反過來依賴它。三者執行起來的路線差不多，差別在程式碼「誰依賴誰」。

箭頭代表「誰用到誰」，實線是直接用到某個具體的程式，虛線是只依賴一份規格（介面）。留意綠色的業務邏輯有沒有往外指的箭頭，以及換資料庫、寫測試時，哪些方塊被標成「要改」或「綁住」。

重點整理

三層式（Layered）
最直覺也最常見：畫面層用業務層，業務層用資料層。但業務邏輯直接依賴資料庫的程式，換資料庫或想不接資料庫來測試時，業務邏輯就會被牽動。
為什麼這樣設計把畫面、規則、資料分開，結構好理解，不同專長的人也能各負責一層。以新增、查詢、修改資料為主的系統，規則本來就很簡單，多加一層規格反而是負擔。
六角架構（插座與插頭）
業務核心自己定好需要的「插座規格」（介面），資料庫、網頁入口、訊息佇列都做成插頭接上來，由 main 在啟動時組裝。換資料庫只是換一個插頭。
為什麼這樣設計它的發明者希望程式「不靠畫面、不靠資料庫」也能執行和測試。把外部世界都當成可以替換的插頭，業務核心就能獨立演進，換框架、換資料庫都不必動到它。
Clean Architecture（洋蔥式）
和六角架構同一個家族，再把核心細分成「企業規則」和「應用流程」，像洋蔥一圈一圈，依賴只能由外往內。分得越細越能隔離變化，也越容易對小專案過度設計。
為什麼這樣設計大型、會用很多年的系統裡，框架、資料庫、畫面都可能換好幾輪，只有業務規則一直留著。把最穩定的東西放最裡面，越外圈越容易替換。
關鍵：依賴反轉
三種做法的差別，都來自同一件事：讓重要的業務規則依賴「規格」，而不是依賴某個具體的資料庫或框架。執行時的呼叫方向不變，程式碼的依賴方向反過來。
