前端呼叫 API：同步 vs 非同步

生活情境打開網頁，資料還沒載完整個畫面就卡住，點什麼都沒反應；或是搜尋時，畫面突然跳回舊的結果。

打個比方同步像在餐廳櫃台點完餐就站著等，後面的人全部卡住；非同步像拿了取餐號碼牌，先回座位做別的事，叫號再去拿。

這頁比較網頁向後端要資料的三種寫法：原地等、拿號碼牌一個一個等、拿號碼牌一次全部點。

網頁上負責畫畫面、處理點擊的只有一個「工人」（主執行緒）。如果它停下來等網路回應，畫面就凍住了。非同步讓它在等待時先去做別的事。但同樣是非同步，請求要排隊還是一起發、出錯和回應順序亂掉怎麼處理，結果差很多。

每個面板是一條時間軸：最上面是主執行緒，紅色斜紋代表它被卡住；下面是每一份資料的等待時間。留意同一個時間點三邊誰在等、誰被卡住，以及最後畫面顯示的是不是正確的結果。

重點整理

同步呼叫（原地等）
發出請求後停在原地等回應。程式最好寫，但等待期間畫面凍住，點擊、打字都要等到回應回來才有反應。現在的瀏覽器已經不建議這樣寫。
為什麼這樣設計早期還沒有方便的非同步寫法，原地等可以照「一行接一行」的順序寫程式，最好理解。在伺服器或背景程式裡仍然常用，因為那裡被卡住的不是使用者的畫面。
非同步：逐一等待
等待時畫面照常可用，但一次只等一個請求，前一個回來才發下一個；彼此沒關係的請求也要排隊，總時間是每一個相加。
為什麼這樣設計async／await 讓非同步程式寫起來跟同步一樣好讀，是最自然的第一步。當後一個請求真的需要前一個的結果（例如先登入拿到通行證，再查資料），逐一等待正是正確的寫法。
非同步：並行＋防護
彼此沒關係的請求一起發，總時間只取決於最慢的那一個；一份出錯不影響其他份；會被新輸入取代的請求（例如搜尋），新的來了就取消舊的。
為什麼這樣設計使用者感受到的快慢，取決於「最後一塊畫面出現的時間」，一起發能把它從相加縮短到最慢的那一個。網路回應的順序也不保證，所以只要畫面會被連續觸發，就得主動處理過期的回應。
Promise.all 和 allSettled
Promise.all 只要一份失敗，整個就算失敗，成功的那幾份也拿不到，適合缺一不可的資料。Promise.allSettled 會等全部結束，分別告訴你誰成功誰失敗，適合頁面上各自獨立的區塊。
